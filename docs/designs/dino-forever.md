## Problem Statement

Build a public web page that plays with zero clicks: Chrome's own T-Rex runner game plays itself,
learns from every crash, and keeps running indefinitely. Anyone who clicks the GitLab link
watches it live, with beautiful real-time visualizations of the training and a live
global board. No heavy ML or UI frameworks. The user's bar: "should be the best dino project
that ever made."

## What Makes This Cool

- **It's the real game.** It runs Chromium's own T-Rex runner code, pinned and unmodified,
  not a Pygame clone. Existing dino-AI projects either clone the game or drive Chrome with a
  single screenshot bot.
- **The learning is visible.** A ghost swarm of about 150 translucent dinos dies off
  generation by generation. The champion's NEAT brain lights up as it jumps. A graveyard
  shows every crash, and any crash can be replayed exactly.
- **"Never crash" is a public claim with proof and a bounty.** The page shows a shared
  *time since last crash* clock, backed by an endurance gate. In attack mode, visitors try
  to kill the champion with legal obstacles. Every kill trains the next champion, and a
  board ranks the killers.
- **Everyone watches the same run.** The server broadcasts a checkpoint plus the time.
  Every browser reproduces the same run, frame for frame.

## Constraints

- Hosting: code and page live on **GitLab** (gitlab.com, SSH push, GitLab Pages), not GitHub.
- For the visitor: no install and no clicks. Open the link and it's already running.
- No heavy frameworks: plain TypeScript, with esbuild as the only build tool. Zero runtime
  dependencies in the browser. The server uses `node:http` directly.
- "Use the existing Chrome dino game itself." No reimplementation of the gameplay.
- A web page can't script the real `chrome://dino` tab; the browser forbids it. So the
  literal-Chrome demo is a local-only script that drives Chrome over the DevTools Protocol
  (CDP).
- Budget: GitLab free tier CI minutes (about 400/month on shared runners; verify) and one
  small Fly machine.

## Premises (agreed)

1. **Real game, untouched.** Chromium's T-Rex runner source is vendored (copied into the
   repo) at a pinned commit, with its BSD-3 license and without edits.
   - The champion view runs that code **exactly as shipped**, with only the environment
     around it controlled.
   - The only outside interventions are:
     - the hook swaps in a no-op 2D context during fast-forward;
     - in attack forks only, the hook injects legal obstacles;
     - in attack forks only, the hook holds back `Horizon`'s natural obstacle spawning
       (a prototype-level wrapper in `src/hook/attack.ts`, covered by determinism tests).
   - The live run is never injected into.
   - The swarm needs its own update loop. That loop is ours, it is labeled as ours, and it
     calls the vendored `Trex`, `Horizon`, `Obstacle` and `checkForCollision` code.
   - A local script also plays the literal `chrome://dino` in the user's Chrome.
2. **All learning is TypeScript NEAT.** The same code runs in the browser, in the headless
   Node trainer, and on the server. No ML framework. Charts are hand-drawn on canvas.
3. **"Never crash" means runs forever.** Once the game reaches `MAX_SPEED`, it stops getting
   harder, so "forever" can be tested. Proof comes from three things:
   - an endurance gate;
   - a live *time since last crash* clock;
   - any live-run crash gets recorded, becomes training data, and visibly restarts the clock.

   The user rejected a 99,999-score target.
4. **Zero-click wow.** The link opens straight into the champion playing, with the swarm
   training live beside it.
5. **Live global board on a small Fly.io server.** The server replays every submission
   before accepting it, and never trusts a number a client sends.
6. **Determinism.** The hook layer controls the game's clock (fixed 1/60 s steps), its
   randomness (a seeded generator), its screen size (a fixed logical 600×150 canvas) and
   the device flags. As a result, a run replays identically in the browser, in Node and on
   the server. The `chrome://dino` demo runs in real time and is labeled live-only.

## Cross-Model Perspective (Claude subagent, cold read)

- **Coolest version:** make the world the adversary. Visitors get a budget of *legal*
  obstacle drops to try to kill the champion. Kills are replayed on the server and feed the
  next generation's training. The board ranks killers ("Champion v37 has survived 18,203
  attacks from 4,100 humans"). **Adopted.**
- **What excites the user:** "never crash the cactus which means it should be able to run
  forever, and give a live global board." The thrill is public, provable immortality.
- **Prior art that gets us halfway:** wayou/t-rex-runner as the extraction reference, and
  neataptic (archived) as a NEAT reference to port to TypeScript with zero dependencies.
- **Challenged premise #6:** the runner uses `performance.now()` for `deltaTime` and
  `Math.random` for obstacles. We adopted the fix in the hook layer. It also flagged the
  swarm patch size, and the risk that NEAT plateaus on tight combinations that need
  fast-fall.
- **First move:** build the headless harness and a scripted oracle before any NEAT code.
  **Adopted as Milestone 1.**

## Recommended Approach: B — Proven Immortal

One engine, three places: the browser, a headless Node trainer, and the Fly server.

### Engine and determinism

- **Vendoring and bundling.** We pin the newest Chromium revision of the T-Rex runner
  (currently the ES modules under `components/neterror/resources/dino_game/`) and record the
  layout in VENDOR.md. esbuild bundles the **unedited** modules into one IIFE per engine
  version.
- **Host scaffold.** The runner expects Chrome's neterror page around it. We provide that
  in `host.html`:
  - the `.interstitial-wrapper` element;
  - the `#offline-resources-1x/2x` sprite `<img>` tags;
  - the audio template;
  - a `loadTimeData` stub.
- **Node shim.** In Node, `src/hook/dom-shim.ts` (our code, zero dependencies) provides a
  minimal DOM (`createElement`, `classList`, listeners) and a no-op 2D context. The bundled
  IIFE runs in a `vm` context, so we avoid `--experimental-vm-modules`.
- **Device flags.** `IS_HIDPI` / `IS_MOBILE` / `IS_IOS` are constants computed at module load
  from `window.devicePixelRatio` and `navigator.userAgent`. The env spoofs **those globals**
  before the bundle loads.
- **Realms instead of monkeypatching.** The runner is a singleton (`Runner.instance_`). Its
  code imports `getTimeStamp` as a module binding, which can't be replaced from outside. It
  also attaches keydown, blur and visibilitychange listeners to the whole document. So each
  runner loads inside its **own realm**:
  - in the browser, a same-origin iframe loading `host.html`. The champion's iframe is
    **visible**: a 600×150 canvas scaled by CSS. The swarm's is offscreen, and its canvas
    content is drawn by our swarm renderer;
  - in Node, a `vm` context.

  In each realm, `env.ts` replaces the *globals* before the vendored code loads:
  - `performance.now`, `Date.now` and `requestAnimationFrame` are driven by our clock;
  - `Math.random` becomes a seeded PRNG (mulberry32, state kept in snapshots);
  - `IS_MOBILE` / `IS_HIDPI` / `IS_IOS` and the canvas size are forced to a fixed **600×150
    logical** size. `setSpeed` therefore never scales for narrow screens; phones scale the
    output canvas only with CSS.

  Document listeners in the realm only ever see synthetic events, so visitor keypresses
  never reach the champion. The intro animation (which waits on a CSS `animationend`) is
  skipped by calling the runner's start path directly. We disable alternate game modes,
  sound and the easter egg through config.
- **Stepping.** Each `step()` advances exactly 1000/60 ms of game time. In the browser,
  rAF only decides *how many* fixed steps to run per animation frame.
- **Context swap.** `env.ts` switches the canvas context between real and no-op. It uses
  no-op for fast-forward, for headless swarm steps, and in Node, so the vendored `update`'s
  draw calls cost nothing.
- **Swarm realm.** It still constructs one headless `Runner`, because `Horizon` and
  `Obstacle` read statics (`Runner.config`, `spriteDefinition`) that `Runner`'s init sets.
  Our swarm loop then drives N vendored `Trex` instances against that runner's `Horizon`.
- **Snapshots.** `snapshot.ts` serializes the full world state:
  - the runner: speed, distance, running time, invert/night state;
  - the dino: y position, velocity, status, jump and speed-drop state;
  - the obstacles: type, x, y, size and gap;
  - the clouds, the distance meter, and the PRNG state.

  A restore followed by N steps must match N steps run straight through (tested). Snapshots
  let anything jump straight to a point in time, so nothing ever has to replay from frame 0.
- **Cross-browser identical math.** NEAT activations use only `+ − × ÷`, via the rational
  sigmoid `0.5 + 0.5·x/(1+|x|)`, so decisions are bit-identical in V8, SpiderMonkey and
  JavaScriptCore. The vendored game physics is already plain arithmetic. We verify it in CI
  anyway (see below).
- **State hash.** A per-frame hash covers the dino's y and status, the obstacles, speed and
  distance. It is used by all determinism and snapshot tests.
- **Engine versioning.** `engineVersion` = vendored commit + hook version. Every stored run
  records it, and the server rejects replays whose version doesn't match. If we ever
  re-vendor, the old engine bundles get archived at `/api/engine/:version`. That is only
  built when a second version actually exists.

### Controls and learning (NEAT in TypeScript)

- **Controls match Chromium's keys.** There are two outputs, `jumpHeld` and `downHeld` (on
  when > 0.5). Rising and falling edges map to the vendored keydown/keyup handling:
  - jump: `startJump`, and `endJump` on release, so jump height depends on hold time, as in
    the real game;
  - down on the ground: `setDuck`;
  - down in the air: `setSpeedDrop` (fast-fall).

  Humans racing use exactly the same mapping.
- **Inputs (normalized).**
  - For each of the next 2 obstacles: `dx / 600`, `width / 100`, `yPos / 150`, and a one-hot
    type (small cactus, large cactus, pterodactyl).
  - The dino's `yPos / 150` and `jumpVelocity / 10`.
  - `speed / MAX_SPEED`, plus a bias of 1.
  - Missing obstacles use `dx = 1` with zeros for the rest.
- **NEAT hyperparameters (starting values, tuned in M2).**
  - Population 150, compatibility threshold 3.0 (c1 = 1, c2 = 1, c3 = 0.4), target 8-12
    species.
  - Weight mutation 0.8 (0.9 perturb σ = 0.5, 0.1 reset), add-connection 0.05, add-node 0.03.
  - Elitism of 1 per species with more than 5 members; stagnation cull after 15 generations.
- **Episodes and fitness.**
  - Each evaluation uses **K = 8** seeds: 5 fresh and 3 from the curriculum.
  - Episodes are capped at **ramp + 36,000 max-speed frames** (10 min of game time), so a
    perfect genome doesn't evaluate forever.
  - K = 8 means **5 fresh full episodes** (cap = ramp + 36,000) plus **3 curriculum
    episodes** (cap = 600 frames from a snapshot).
  - `fitness = mean over the 8 episodes of (frames_survived / that episode's own cap)`.
  - Any curriculum failure multiplies fitness by 0.5, so hard cases dominate selection.
- **Curriculum.** Recorded crashes are:
  - the best-of-generation training crashes;
  - all live-run crashes;
  - all verified visitor kills.

  Each one stores a **snapshot taken 180 frames (3 s) before impact**. Near-identical
  snapshots are deduplicated by obstacle-sequence signature. The curriculum is capped at
  500 cases; when full, the oldest cases the champion already clears drop out first. A curriculum case restores that snapshot and must survive 600 frames. Visitor
  kills are stored the same way.
- **Promotion.** A new champion replaces the live one only if it passes the endurance gate
  *and* every curriculum case in the **clearable set**.
- **Clearability.** A case is clearable if the oracle survives it, *or* if a bounded
  search from the pre-impact snapshot finds a survival sequence.
  - **Search:** a per-obstacle segmented beam search over action primitives: jump with hold
    length in {min, 4, 8, 12, max} frames, duck, speed-drop at offsets {0, 4, 8, 12}, and
    wait. Beam width is 64.
  - **Budget:** 2M simulated frames.
  - **Out of budget:** the verdict is "undecided". An attack is then not credited yet, and
    the case is re-checked on the trainer machine. The search
  covers jump press frame, hold length, duck and speed-drop timing over the 180 + 600
  frames. Only a case both fail is labeled "unclearable": it shows in the graveyard and
  never blocks promotion.

### Proof of "forever"

- **Feasibility.** The oracle sweeps **200 seeds × 1M max-speed frames** (about 4.6 h of
  game time each). If every seed survives, "forever" is physically possible, and a NEAT
  crash where the oracle survives points at NEAT. If a seed kills the oracle, we inspect it.
  If Chromium itself can generate an unclearable combination, the public claim becomes
  "never crashes on any clearable sequence", and the page says so.
- **Endurance gate (full).** 500 seeds, each run until 30 min of game time at `MAX_SPEED`
  (about 108k max-speed frames plus ramp), with zero crashes. It runs on the **trainer
  machine**. The server re-verifies a random 20-seed sample before promotion.
- **CI gate (small).** 10 seeds on merge requests (MRs), to fit GitLab free-tier minutes.
  There is no nightly CI gate.
- **Live run and clock.**
  - The server holds one endless champion run.
  - Every 3,600 frames (1 min) it writes a **checkpoint** (snapshot + frame number) to
    SQLite, and sends the latest one over SSE.
  - The run's current frame is `floor((now − startEpoch) × 60)`.
  - Clients and a restarted server restore the latest checkpoint and fast-forward at most
    about 60 s of frames. That's under 0.5 s at 10k frames/s, so it meets the 2 s load
    target on any day of the run.
  - The clock covers **only the live run**. Attacks, races and training crashes never touch
    it.
  - If the live run crashes, the crash is recorded, added to the curriculum, and training
    continues. The live run restarts on a new seed, and the clock visibly restarts at zero.
  - On **promotion**, the new brain takes over at the next checkpoint. The world state
    carries on, and the clock does **not** reset, because no crash happened. The page
    announces "Champion v38 took over".
  - Every checkpoint records `championVersion` and `engineVersion`.

### Page (GitLab Pages, static)

Wireframe: `~/.gstack/projects/chrome-dino/designs/sketch.png` (source: `sketch.html`).

- **Row 1 (zero-click).** The champion plays the vendored runner, in sync with the server's
  live run. Beside it: the big *time since last crash* clock, the endurance-gate badge, and
  the **Try to kill it** and **Race it** buttons.
- **Row 2.**
  - Left: the ghost swarm. This tab runs its own live NEAT evolution at ×1/×4/×16, colored
    by species. Clicking a ghost opens its brain in the brain panel.
  - Right: the live brain. The champion's network is drawn with nodes lit by activation and
    the output that fired highlighted.
- **Row 3.**
  - Left: the graveyard. It shows the best-of-generation crashes, live-run crashes and
    visitor kills; clicking one restores its snapshot and replays the 3 s before impact.
    Below it sits a best/mean fitness chart on a log scale.
  - Right: the global board, with longest survival, top killers, fastest human records and
    live counters.
- **Syncing and offline.** On load, the page takes the latest checkpoint from SSE, restores
  it, fast-forwards and renders. It does the same when a hidden tab becomes visible again.
  Pages ships a snapshot `champion.json` and `history.json`. If the server is unreachable,
  the bundled champion plays a local run, labeled "offline", and the board shows
  "reconnecting…" with the last-known numbers greyed out. If the bundled champion is older
  than the server's, the server always wins.
- **Details.** Muted by default. The game renders at 600×150 logical size, scaled by CSS;
  on phones the panels stack below it. Targets: browser JS under 300 KB gzipped, and 150
  swarm dinos at 60 fps on a mid-range laptop.

### Attack mode and race mode

- **Attack UX.** The visitor clicks **Try to kill it**. A fork of the champion starts from
  the latest live checkpoint (never the live run itself). The visitor gets a budget of
  **10 drops**; each drop is placed by clicking an obstacle palette as the game runs. The
  fork plays 60 s. The result shows on screen immediately, and the server confirms it.
- **Drop format.**
  ```json
  POST /api/attack
  {"engineVersion":"…","championVersion":37,"checkpointId":"…",
   "drops":[{"frame":1234,"type":"CACTUS_SMALL|CACTUS_LARGE|PTERODACTYL","size":1,"yPos":100}],
   "handle":"sam"}
  ```
  At frame `f`, a drop builds the obstacle with the vendored `new Obstacle(...)`, overwrites
  its `size` / `yPos` / `gap` with the requested values, and pushes it onto
  `horizon.obstacles`. The random draws the constructor already consumed stay consumed, so
  replay remains deterministic. Natural spawning is suppressed until the drop's gap is
  cleared. The oracle and brute-force search run from the same checkpoint with the same
  drops. A drop is legal only if:
  - the type, size and `yPos` are values Chromium's generator can produce at the current
    speed (pterodactyls only above their minimum speed);
  - the `xPos` distance from the last obstacle is at least the generator's `minGap` at the
    current speed;
  - the number of drops is within the budget.

  A kill counts only if the sequence is clearable, as defined above. Otherwise the response
  is "unclearable, not a kill". A kill is confirmed within seconds. **Retraining and
  promotion against it takes hours to days**, and the page says "patch in progress". Accepted kills are credited, stored as curriculum snapshots
  and shown in the graveyard.
- **Race UX.** The visitor clicks **Race it**. The visitor and a ghost of the champion play
  the **same seed** side by side, and the visitor controls the game with Space / ↓.
  ```json
  POST /api/run
  {"engineVersion":"…","seed":123,"inputs":[{"f":120,"k":"jump","d":1},{"f":131,"k":"jump","d":0}],"handle":"maya"}
  ```
  The server replays the run and records the verified frames survived.
- **Handles.** 3-16 characters, word-filtered, stored in localStorage. They are display
  names only, not accounts or authentication. The server keeps a moderator hide list.

### Server (Fly.io)

- **Stack.** `node:http` plus SQLite (WAL mode) on a volume. No framework.
- **Endpoints.**
  - `GET /api/live` is a server-sent events (SSE) stream carrying checkpoints, crashes,
    promotions, counters and a heartbeat. It supports `Last-Event-ID` reconnect: the
    client resumes and gets the latest checkpoint.
  - `GET /api/stats`, `/api/history`, `/api/graveyard`, `/api/champion/:v`, `/api/board`,
    `/api/curriculum`.
  - `POST /api/candidate`, which needs the trainer's deploy key.
  - `POST /api/run` and `POST /api/attack`, as above.
- **CORS.** Allow the Pages origin `https://kumarganduri.gitlab.io` only.
- **Abuse limits.** Rate limits per IP. Payloads over 32 KB are rejected. Each replay gets a
  CPU budget: at most 1M frames, with a 5 s cap on its worker thread.
- **Training runs off-server, verification runs on it.** A cheap Fly machine has a small
  sustained CPU baseline, so a full gate (~55M frames) or one late-stage generation
  (~48M frames) would take about a day there.
  - **Where training runs:** the trainer and the full endurance gate run on the **Mac**
    (8+ cores, `trainer/` with worker_threads), or later on a rented spot box.
  - **What the trainer uploads:** it sends `POST /api/candidate` with a signed deploy key
    (a secret on the Mac). The upload holds the genome, the gate results (seed list plus
    per-seed hashes), and the generation history.
  - **What the server checks:** before promoting, it re-verifies a random sample of
    **20 gate seeds** and every clearable curriculum case.
  - **What the server itself runs:** the live run, checkpoints, SSE, and replays of attacks
    and races, all within per-replay CPU budgets.
  - **The page's "training" views:** the "server generation" counter and history chart
    show the latest uploaded training state. The swarm in each visitor's tab is live
    training running right there.
  - **Continuous training:** the Mac trainer can run as a background job (`launchd`),
    pulling new curriculum cases from `/api/curriculum` on every generation.
- **Machine size.** Start with a Fly shared-cpu-1x plus a 1 GB volume. Upgrade only if
  replay latency needs it. Check current Fly pricing first.

### Local "the real thing" demo

`node scripts/real-chrome.mjs` works like this:
- It starts the user's Chrome with `--remote-debugging-port` and a throwaway profile, then
  opens `chrome://dino`.
- It sends Space to create the game, then injects the sense/act loop and the champion's
  network.
- It is labeled "live, real-time, not replayable". The real-time `deltaTime` differs from
  training, so the champion is evaluated here as-is. If it proves fragile, we add
  jittered-`deltaTime` evaluations to training (in M4, only if needed).
- A probe on 2026-09-28 confirmed CDP can reach `chrome://dino` (the page URL is
  `chrome-error://chromewebdata/`, `typeof Runner === 'function'`). The instance only
  exists after the first keypress.

## Reviewer Concerns (to resolve with M1 measurements)

1. **Server CPU budget.** If Fly shared-cpu-1x sustains only about 600 frames/s, then:
   - the 20-seed candidate re-verification (~2.2M frames) takes about 1 h;
   - attack confirmation (fork + oracle + search) can't meet "within seconds";
   - the 60 s fast-forward after a restart takes about 6 s.

   **Resolution path:** measure frames/s on the real Fly machine in M1. Run candidate
   re-verification as a separate background job with no replay cap and no latency promise.
   Set the attack confirmation target from that measurement. If needed, run a
   performance-1x machine or move verification to the trainer box and sign the results.
2. **Beam search cost.** The clearability search budget (2M frames) is a guess, and so are
   the primitives. Tune both on real curriculum cases in M3 before attack mode goes live.

## Success Criteria

- On a cold load, opening the Pages link shows the champion playing within 2 s, with no
  clicks, on both desktop and phone, including 30+ days into a live run.
- Determinism: the same `(engineVersion, genome, seed, inputs)` produces identical
  per-frame hashes in Node, Chromium, Firefox and WebKit, and a restore from a snapshot
  matches a straight run. Enforced in CI.
- The oracle sweep (200 seeds × 1M max-speed frames) either passes, or documents each
  unclearable sequence.
- The published champion passes the full endurance gate: 500 seeds × 30 min at
  `MAX_SPEED`, zero crashes.

6. **Full random-number parity (tension 1).** `loop.ts` makes the same random-number calls, in the same order, as `Runner.update`, including clouds, stars and background. The per-frame hash includes `rngCallCount`, so a drift is caught on the exact frame it starts.

1. **Headless = Chrome's genuine `Runner.update`** (supersedes eng decision 2A's restated loop). `Runner.update` only touches canvas, rAF and the night-mode class. 6. **Two browser bugs found by previewing the page and fixed.**
   - Chrome's `Runner` self-scheduled with the real rAF, which caused extra updates.
   - `Runner.stop()` cancelled the page's real rAF id 1, which froze the champion view.

   Both are covered by regression tests.
